# WebDAV + SQLite 同步机技术方案（借鉴 Joplin 概念）

**状态**：设计文档，尚未在代码中落地。  
**目标**：在保持 WebDAV 作为「远端文件存储」的前提下，引入与 Joplin 文档中类似的 `**sync_items` 与 item 生命周期** 概念，用统一的「列目录 → diff → 下载 / 上传」循环替代分散的同步分支，使个人多设备场景下同步更可控、可观测、可回归测试。

**非目标**（本阶段明确不做）：

- 与官方 Joplin 客户端**共用同一套远端目录**或**二进制互操作**（除非后续单独立项）。
- 端到端加密（E2EE）。
- 类 Google Docs 的**实时协同**与 CRDT 全文合并（另见业务决策）。
- 将 WebDAV 替换为其他协议（可保留 `SyncClientBase` 抽象，但本文以 WebDAV 为主）。

**参考**：[Joplin 同步开发规范 - Synchronisation](https://joplinapp.org/help/dev/spec/sync)（仅借鉴架构词汇与流程，非实现 Joplin 文件格式。）

---

## 1. 背景与问题

当前实现已具备：WebDAV 客户端、按 `uuid` 分片的笔记 JSON、图片与分类文件的分离存储、基于时间与内容指纹的冲突处理。随着逻辑分散在增量同步与单条同步路径中，易出现：

- **规则重复**（何时上传、何时下载、何时跳过）难以在一处维护。
- **部分失败**时，本地与远端、以及 `sync_meta` 状态**不易对齐**。
- 难以用一张表**枚举「还有哪些 item 未与远端一致」**。

Joplin 式思路的核心是：**每个可同步对象是一条「item」**，用 `**sync_items`** 记录其相对「当前 sync target」的生命周期，由**单一 Synchronizer** 驱动，远端仅提供**列目录、读、写、删**能力。

---

## 2. 核心概念

### 2.1 Item（同步单元）

在本文范围内，**item** 指一次同步中**可独立做版本与状态跟踪**的单元。与本应用现状对齐的建议划分：


| 类型               | 说明            | 备注                                         |
| ---------------- | ------------- | ------------------------------------------ |
| `note`           | 单条笔记的 JSON 文件 | 路径与现有 `benny/notes/{shard}/{uuid}.json` 一致 |
| `image`          | 内嵌资源文件        | 路径与现有 `benny/images/{filename}` 一致         |
| `category_index` | 全部分类的聚合文件     | 如 `benny/meta/categories.json`             |


**说明**：若图片继续仅由笔记「顺带」上推，也应在 `sync_items` 中可为图片单独建项，或至少定义「从属关系」，便于重试与跳过未变更资源。

**Item 主键**建议：`item_type` + 稳定 id（如笔记用 `uuid`，图片用 `filename` 或 hash 命名后的 id）。

### 2.2 Sync target

当下**仅一种**：用户配置的 **WebDAV 根路径下的 `benny/` 约定目录**。若未来支持多个远端（多账号 / 多服务器），`sync_items` 需增加 `sync_target_id`（本阶段可预留，不实现多目标 UI）。

### 2.3 `sync_items` 表（逻辑模型）

以下为**逻辑字段**草案，具体列名、类型、索引在实现阶段与 `lib/dao/db.dart` 迁移一起定稿。


| 字段                                             | 说明                                                        |
| ---------------------------------------------- | --------------------------------------------------------- |
| `item_type`                                    | `note` / `image` / `category_index` 等                     |
| `item_id`                                      | 与 item 类型对应的稳定标识                                          |
| `local_updated_at`                             | 本地认为的内容或文件变更时间（可选，可与业务表统一）                                |
| `last_full_sync_at` 或 `last_synced_at`         | 上次**认为与远端该 item 已对齐**的时间（语义需在实现中写死）                       |
| `local_sync_status`                            | 生命周期状态（见下）                                                |
| `remote_etag` / `remote_mtime` / `remote_size` | WebDAV 能取到的**尽可能稳定**的远端元数据，用于「是否需下载」的判定；若不可靠则回退为下载后比 hash |
| `last_error` / `error_count`                   | 最近失败信息（控制重试与 UI 提示）                                       |
| `content_hash`（可选）                             | 与现有 `note_sync_contentHash` 对齐，用于跳过无意义上传                  |


**多目标时**：增加 `sync_target_id` 外键或等价字段。

### 2.4 Item 生命周期（状态机）

状态命名可为内部枚举，**需在代码注释与本文档中双向对齐**。示例：


| 状态                         | 含义（简述）                            |
| -------------------------- | --------------------------------- |
| `clean`                    | 本地与远端在约定规则下**一致**（或近期已确认一致）       |
| `dirty_local`              | 本地有未上传变更                          |
| `pending_remote` / `stale` | 已知或怀疑远端较新，待拉取后合并或覆盖               |
| `conflict`                 | 需要用户或策略解决（与现有冲突对话框可衔接）            |
| `delete_pending`           | 本地或远端删除需传播（若采用 tombstone，与删除策略绑定） |
| `sync_skipped`（可选）         | 用户或策略禁止同步该项                       |


**迁移规则**（在实现时应用代码 + 单测固化为列表）：例如**本地编辑** → `dirty_local`；**列目录发现远端 mtime 新** → 进入 `pending_remote` 或拉取后进入 `conflict`；**成功 PUT 且校验一致** → `clean`。

## 3. 同步管线（列目录 → diff → 上 / 下）

### 3.1 单一入口：Synchronizer

- **输入**：取消信号、进度与日志回调。  
- **阶段**（顺序可微调，但**必须文档化**）  
  1. **列远端**：对 `benny/notes/*`、`benny/images/`、`benny/meta/` 等**列举**并建立**路径 → 元数据**索引。
  2. **加载本地**：从 SQLite 得到待同步的 item 列表与 `sync_items` 状态。
  3. **Diff**：为每个 item 判定 **仅上传** / **仅下载** / **需冲突流** / **跳过**。
  4. **执行**：先处理强依赖项（如分类与笔记的依赖关系与当前产品一致时保持「先分类后笔记」等）。
  5. **收尾**：更新全局 `last_sync_at`（若保留）、**批量回写** `sync_items` 与必要的 `sync_meta`。

### 3.2 Diff 判定原则（与现有一致性）

- 继续保留 `**noteSyncContentHash`** 与 `**updatedAt**` 的分工：时间戳相同时以 hash 或策略为准。  
- **跳过**：本地 `clean` 且远端元数据未变（在 etag/mtime 可信时）。  
- **列目录**失败：整体策略（重试 / 中止 / 只读本地）需**单一分支**，避免与当前多处 `print`+继续混用长期并存。

### 3.3 失败与部分成功

- 定义：**一轮同步结束**时，向 UI 报告「成功 / 部分失败 / 全失败」及**失败 item 列表**。  
- 每个 item 在 `sync_items` 中独立记录**错误原因**，支持**重试**而不必全量重扫（可与指数退避策略结合，后续迭代）。

### 3.4 与现有 `IncrementalSync` / `SingleNoteSync` 的关系

- 长期目标：上述逻辑**收敛**到 Synchronizer；单条 API（若保留）**仅**作为「对单 item 的快捷调用」薄封装，**不得**再维护第二套 diff 规则。  
- 迁移期：允许**双写** `sync_items` 与旧 `sync_meta`，以开关或迁移脚本收口。

---

## 4. WebDAV 侧约定（不变更目录语义则仅做索引）

- **路径规范**：继续沿用 `benny/notes/{shard}/`、`benny/images/`、`benny/meta/categories.json` 等，除非另有迁移文档。  
- **列举性能**：大目录时考虑**按 shard 懒列举**或**后台缓存远端列表**（属优化，见后文）。  
- **元数据可靠度**：部分服务商对 `ETag`/`PROPFIND` 表现不一；**实现时需 fallback**：不可靠则以下载后比 hash 为准。

---

## 5. 数据迁移与兼容

1. 首次安装新表时：为已有笔记/资源**回填** `sync_items`（缺省可标为 `dirty_local` 或经一次对比后标 `clean`）。
2. 从仅 `syncStatus`+`sync_meta` 的上线版本升级：**迁移脚本**顺序必须写进 `db.dart` 的 migration 与本文档的修订记录。
3. **回滚策略**：若新版本同步失败，是否可关闭「新同步机」并回退旧逻辑（**可选**，视产品要求）。

## 6. 可观测与调试

- 单次同步**摘要日志**：列目录条目数、上/下/跳过的计数、失败 item 列表。  
- 开发模式下的**详细协议日志**可开关，避免生产刷屏。  
- 设置中可选展示：**上次完整成功同步时间**、**未处理冲突数量**（若存在 `conflict` 状态）。
